# mjt-shares

Static, encrypted shares generated by Memex.

This repository is a publication target, not a private store or authoring
workspace. GitHub Pages serves a small browser reader and immutable encrypted
objects. The bearer key belongs only in the URL fragment and must never be
committed here.

## Current status

Operational proving ground. Automated immutable-data publication is active, and
the first real GitHub Pages deployment has been checked through the browser
consumer path. Treat both the repository and its Pages output as public.

## Initial Pages configuration

Use GitHub Pages **Deploy from a branch** with:

- branch: `master`
- folder: `/(root)`

This repository exists only for the static published tree, so a second
`gh-pages` branch would duplicate state without buying useful isolation. The
published branch is the inspectable source of truth. If this repository later
gains source code or a build pipeline, reconsider that choice rather than
quietly mixing source and generated output.

GitHub still documents both `/(root)` and `/docs` as branch-source folders. Root
is intentionally simpler here; `/docs` is not required.

The expected project-site base is:

```text
https://matthewjosephtaylor.github.io/mjt-shares/
```

That `/mjt-shares/` prefix is an HTTP deployment detail, not part of an encrypted
object's canonical identity. Browser transports map canonical
`/share-data/v1/...` paths beneath the project-site base. Unit tests and the
first real Pages publication verify that mapping.

## Published layout

```text
.nojekyll

share/v1/
  index.html                         current chat presentation shell
  social-card-v1.jpg                 generic encrypted-share social preview

share-data/v1/
  <shard>/<storage-index>/
    manifest.bin                    encrypted root manifest
    objects/...                     immutable encrypted objects
```

Presentation code and encrypted objects are released independently. The
encrypted asset tree is presentation-neutral: `share/v1/` is the first chat
presentation shell, not a universal chat-shaped storage contract. Future static
pages, games, media viewers, and other presentation layers may use their own
versioned shells while reusing the same asset loader and `/share-data/v1/`
objects.

Compatible chat-reader fixes stay under `share/v1/`; an incompatible reader or
protocol gets a new versioned path. `share/v1/index.html` and its social card are
generated from the Think workspace reader at commit `6cedd1f1`; do not hand-edit
them.

The crawler-facing title, description, and image are deliberately generic.
URL fragments never reach the HTTP server, so social previews disclose no
share-specific title or decrypted content. The versioned JPEG URL also avoids
stale social-image caches when a future card replaces it.

GitHub Pages may content-encode `.bin` responses. Browser readers therefore
bound the decoded stream rather than comparing an encoded HTTP
`Content-Length` to the authenticated decoded-object limit.

## Security and retention

- Anyone with the complete fragment-bearing URL can decrypt that share.
- URL fragments are not sent in HTTP requests, but they can remain in browser
  history, bookmarks, screenshots, messages, and recipient copies.
- Git commits contain ciphertext and nonsecret routing data only—never
  plaintext drafts, bearer keys, full secret URLs, credentials, or tokens.
- Removing a live file is not revocation. Git history, caches, forks, clones,
  and recipient copies may retain the ciphertext indefinitely.
- Reader pages must load no analytics, advertisements, or third-party runtime
  resources.

## Publication rules

1. Stage and fully verify each publication outside this repository.
2. Add only its immutable ciphertext paths in one focused commit.
3. Never overwrite an existing publication path or force-push `master`.
4. Preserve unrelated repository work.
5. A copied link may be available after Git accepts the commit, but the UI must
   call it **Deploying**, not **Live**, until the exact Pages reader and encrypted
   objects verify through HTTPS.

Reader releases remain deliberate code releases; encrypted object publication
is automated and create-only.
